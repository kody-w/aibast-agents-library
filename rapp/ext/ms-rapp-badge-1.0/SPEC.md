# ms-rapp-badge/1.0

**A convention for publicly verifiable achievement badges served entirely from
static files — no accounts, no badge server, no privileged lookup.**

Status: **draft standard**, originated in the ms-rapp distribution.
Builds on [`rapp-static-api/1.0`](../../standards/rapp-static-api-SPEC.md).
Requirement terms are [RFC 2119]/[RFC 8174]. JSON is [RFC 8259].

Reference implementation: this repository —
[`badges.json`](../../../badges.json), [`certified.json`](../../../certified.json),
[`scripts/build_api.py`](../../../scripts/build_api.py),
[`wall.html`](../../../wall.html).

---

## 1. Why this exists

A badge that cannot be checked is a claim. A badge checked through a login is
a claim plus a dependency. This profile makes the check a plain `GET` of a
static file, so a badge in someone's README is *live*: it reflects the issuer's
current position, and it keeps working when the issuer's servers do not,
because there are none.

It also fixes the failure mode most badge systems get wrong — see §6.

## 2. Roles

| Role | Definition |
|------|------------|
| **Issuer** | The repository that publishes the endpoints. Its git history is the audit trail. |
| **Subject** | The person a badge is awarded to, identified by a platform username. |
| **Verifier** | Anyone. A verifier needs only the subject's username and the issuer's base URL. |

## 3. Inputs (hand-authored)

An issuer MUST maintain exactly two hand-edited documents. Everything else is
generated by the single build step required by `rapp-static-api/1.0`.

**Catalog** (`badges.json`, schema `aibast-badge-catalog/1.0` or an issuer
equivalent) — one entry per badge:

| Field | Req | Meaning |
|---|---|---|
| `id` | ✅ | Stable, lowercase, `[a-z0-9-]`. MUST NOT be reused or repurposed. |
| `name` | ✅ | Display name. |
| `summary` | ✅ | One line: what it says about the holder. |
| `criteria` | ✅ | What must be true to earn it — testable, not aspirational. |
| `points` | ⬜ | Ordering weight only. Carries no other meaning. |
| `tier`, `color`, `how` | ⬜ | Presentation and next-step guidance. |
| `retired` | ⬜ | `true` retires the badge. Existing holders KEEP it. |

**Roster** (`certified.json`) — one entry per subject, each holding an array of
awards (`id`, `awarded_on`, optional `discussion`, optional `note`), plus a
`status` of `active` or `revoked`.

## 4. Generated endpoints

Under the issuer's versioned API root:

| Endpoint | Answers |
|---|---|
| `badges.json` | The catalog, with holder counts. |
| `badges/{badge_id}.json` | Who holds this badge, and when they earned it. |
| `certified.json` | The full roster. |
| `certified/{username}.json` | **Everything one subject has earned.** The verification endpoint. |
| `certified/{username}/badge.json` | Shields-format endpoint for the subject overall. |
| `certified/{username}/{badge_id}.json` or `/badge.json` | Shields-format endpoint for one achievement. |
| `wall.json` | Ranked public roll of subjects holding at least one live award. |

Rules:

1. **Usernames are normalized to lowercase** in both paths and payloads.
   Platform usernames are case-insensitive; verifiers MUST lowercase before
   constructing the URL.
2. Every generated document MUST carry `protocol: "ms-rapp-badge/1.0"`, its
   own `schema`, and a `generated` timestamp (ISO-8601 UTC).
3. An award naming a `badge_id` absent from the catalog **MUST be ignored**,
   never rendered from guessed metadata. An issuer that invents a badge on
   read cannot be audited.
4. Badge endpoints MUST be readable cross-origin (inherited from
   `rapp-static-api/1.0`).

## 5. Verification

```bash
BASE=<issuer api root>
curl -s "$BASE/certified/$(echo "$USER" | tr 'A-Z' 'a-z').json" \
  | jq '{username, certified, badges: [.badges[].id]}'
```

A verifier MUST treat all three of these as **"not certified"**, not as errors
to retry:

- `404` — no roster entry exists for that username;
- `certified: false` — an entry exists and was revoked;
- an award whose `id` is not in the catalog.

A verifier MUST NOT infer certification from the presence of a badge image.
The image is a rendering of the endpoint, not evidence.

## 6. Revocation — the rule that makes this trustworthy

**A roster entry MUST NOT be deleted when an award is withdrawn.** The entry
is retained with `status: "revoked"`, so its endpoint keeps resolving and
answers `certified: false`.

This is the point of the profile. If revocation deleted the entry, the URL
would `404` — and a `404` is indistinguishable from a CDN miss, a rename, or
an outage. A verification system whose "no" cannot be told apart from its
"unreachable" does not verify anything. An explicit negative answer can.

Consequently a badge already embedded in a README flips to *not certified* on
the next build, with no action by the subject and no dead image.

## 7. Provenance and consent

- An award MAY carry a `discussion` URL: the public thread where it was
  granted. That thread is where others congratulate or contest it, which puts
  the award in the open rather than in a private ledger.
- Rosters MUST carry **role and achievement data only** — username, badge ids,
  dates, public links. No email addresses, no employer identifiers, no
  internal identifiers.
- Issuers MUST state plainly what a badge does **not** mean. Certification by
  an issuer is not an endorsement by that issuer's parent organization.

## 8. Conformance

An implementation is **ms-rapp-badge/1.0 conformant** if:

- [ ] Catalog and roster are the only hand-edited inputs; one build step
      generates every endpoint.
- [ ] Every generated document carries `protocol`, `schema`, and `generated`.
- [ ] `certified/{username}.json` resolves for every roster entry, including
      revoked ones, and its `certified` field is the authoritative answer.
- [ ] Revocation retains the entry (§6); removal from the roster prunes the
      endpoint.
- [ ] An award naming an unknown badge id is ignored.
- [ ] Badge ids are never reused or repurposed; retirement preserves holders.
- [ ] Endpoints are static, CDN-cached, and CORS-open.
- [ ] The roster carries no personal data beyond a public username.

## 9. Relationship to RAPP/1

This is an **extension**, not a revision. It defines no wire format, identity,
or agent semantics, and it neither depends on nor modifies any part of
[RAPP/1](../../spec/RAPP1-SPEC.md). An implementation may adopt this profile
without adopting RAPP/1, and vice versa.

It is the first specification originated by the ms-rapp distribution rather
than mirrored from the upstream kernel. Extension governance — how a
downstream-originated profile is versioned, and how it is offered upstream for
consideration — is in [SUCCESSION.md](../../SUCCESSION.md).

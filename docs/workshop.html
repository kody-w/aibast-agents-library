Step 2 · Know what you're gettingread first

What you're building

A dispatch agent for energy field operations: the queue, the zones, who takes which job, and who responds when a SCADA alarm fires. Before touching the CLI, know where each behavior lives — and what this prototype deliberately leaves out.

Scope — decided up front, not discovered later

In — this build

  • Dispatch dashboard, priority-ranked
  • Zone capacity & utilization analysis
  • Technician recommendations via a deterministic scoring rule
  • Emergency responder identification
  • Certification gating that cannot be talked out of
  • Synthetic data: 5 technicians, 5 requests, 3 zones

Out — deliberately

  • Actually assigning or dispatching anyone — the agent recommends, a person acts
  • Writing to any system of record
  • Real operational data of any kind
  • Notifications or messages to technicians

Later — step 7

  • Live data via SharePoint / Dataverse / D365 Field Service tools
  • Teams channel rollout
  • Per-dispatcher memory
Separate global behavior, facts, actions, procedures, memory, delegation, and code execution.

Step 3 · The easy way~15 min · mostly watching

Say the mission

You steer; your AI executes. It fetches the mission playbook from the public library and runs every command itself — the same steps documented under the hood below. Here is the whole conversation:

  1. You say: “Deploy the … agent to Copilot Studio.”

    The AI checks your machine (installs the Power Platform CLI itself if missing), detects your environment, creates the project, installs the skills and knowledge from the library, and sets the instructions. You watch one-line progress updates.

  2. It may ask you to sign in — once.

    If you have never authenticated, it asks you to run pac auth create in a terminal and finish the browser sign-in with your work account. That is the only technical step a person ever does, and only the first time.

  3. It asks before going live: you say “yes, publish it.”

    Publishing makes the agent live for everyone it's shared with — so that call is always yours.

  4. It hands you the test script.

    Five questions with computed expected answers — that's step 4, and it's yours to click through.

Works for the whole library. Swap the agent name and the same sentence deploys any stack — “deploy the emission tracking agent”, “deploy the permit license management agent”. Ask “what agents can I deploy?” for the full list.

AI-run · DIY insideCreate the project — authenticate, scaffold, bind to the environment

Create the project

Two commands: authenticate, then scaffold an empty CLI-authored agent bound to your environment.

  1. Authenticate the CLI

    Completes a browser sign-in. Use the account with maker permissions in your target environment.

    terminal
    pac auth create
  2. Initialize the agent project

    Replace the environment ID with yours. This creates the field-service-dispatch/ project: settings.mcs.yml plus the behaviors/ and capabilities/ folders you'll fill next.

    terminal
    pac copilot init \
  --name "Field Service Dispatch Agent" \
  --publisher-prefix aibast \
  --authoring-mode cli-copilot \
  --project-dir field-service-dispatch \
  --environment "<your-environment-id>"
  3. Confirm the scaffold

    The project directory now contains settings.mcs.yml. If it doesn't, stop here and fix it — nothing downstream works without it.

Never hand-edit .mcs/. It is CLI-managed sync state. Everything you author lives in settings.mcs.yml, behaviors/, and capabilities/.
Done when field-service-dispatch/settings.mcs.yml exists and carries your environment binding and a generated schemaName — note that schemaName, you need it to publish.
AI-run · DIY insideAdd the components — download the skills, knowledge, and instructions from the library

Add the components

The library ships the component set ready-made in the stack's copilot_studio/ folder — four skills, two knowledge files, and the instructions. Copy them in, then set the instructions.

  1. Copy the skills and knowledge into the project

    Run from the stack folder (where copilot_studio/ lives), with your project as the destination:

    terminal
    cp copilot_studio/behaviors/*.mcs.yml            field-service-dispatch/behaviors/
cp copilot_studio/capabilities/knowledge/files/*  field-service-dispatch/capabilities/knowledge/files/

    What just landed:

    • dispatch-dashboard_fsd101.mcs.yml — priority-ranked queue with filter-aware counts
    • route-optimization_fsd102.mcs.yml — per-zone capacity and the exact utilization formula
    • technician-assignment_fsd103.mcs.yml — the eligibility gates and the scoring rule: score = efficiency + 10 in-zone + 5 not-on-a-job
    • emergency-response_fsd104.mcs.yml — every certified responder listed regardless of status
    • Two knowledge files + sidecars: the synthetic operations data and the certification policy
  2. Set the instructions

    Open field-service-dispatch/settings.mcs.yml. Keep every generated field exactly as pac wrote it — you are only filling the instructions segment with the full contents of the stack's instructions.md:

    settings.mcs.yml — the segment shape
    configuration:
  agentSettings:
    instructions:
      segments:
        - kind: StaticSegment
          value: |
            <paste the full contents of instructions.md, indented to match>
    The six never-relaxed rules you are pasting — know them before you paste them
    • Certification gating is absolute. Never recommend a technician for work requiring a certification they don't hold — not for emergencies, not when nobody else is available, not when asked directly.
    • The agent recommends; a person dispatches. It never states or implies an assignment or notification happened.
    • Critical and emergency work always ranks first.
    • Every claim cites record IDs (TECH-, SR-); the agent never invents records.
    • Missing data is a finding — said plainly, never guessed around.
    • Zone filters apply to everything — tables, counts, and recommendations.
Done when the project holds 4 skill files, 2 knowledge files with their .mcs.yml sidecars, and instructions in the StaticSegment.
AI-run · DIY insidePush & publish — sync in the right order, go live only on your yes

Push & publish

Sync order matters: pull, then push, then publish. Pull merges any remote state first so your push lands clean.

  1. Pull, then push
    terminal
    pac copilot pull --project-dir field-service-dispatch
pac copilot push --project-dir field-service-dispatch

    If push reports a conflict, pull again, resolve, and retry. If it reports nothing to send, your components didn't land — go back to step 4.

  2. Publish

    Use the schemaName from settings.mcs.yml:

    terminal
    pac copilot publish --bot "<schemaName>" --environment "<your-environment-id>"
Publishing makes the agent live for everyone it is shared with. For a prototype that's just you — but make sharing a decision, not a default, before step 7.
Done when publish completes and the agent opens in the Copilot Studio maker portal with your four skills and two knowledge sources visible.
For your architectsThe architecture — a Well-Architected review of what just got built

Runtime and build architecture — your agent

Two lanes. The build lane exists only while you author; the runtime lane is what production traffic touches. Nothing in this design is novel infrastructure — every box is a governed Microsoft service the tenant already runs, which is precisely the argument to make when the curve balls come.

The system-of-record box follows your adventure pick above — the runtime shape is identical for every hookup; only the connector and its authentication provider change.

The five pillars, answered — Microsoft Well-Architected Framework

PillarHow this design answers itWhat to concede honestly
Reliability The agent is stateless between turns; published versions are immutable; the entire definition lives as versioned YAML in git, redeployable to any environment in minutes via pac. Platform SLAs are inherited from Power Platform, not built. The computed verification set is a regression suite — rerun after every change, forever. A Copilot Studio service outage takes the runtime with it (we hit one live: the ecs.office.com config 503 disables the test surface). There is no self-hosted fallback — the mitigation is the documented outage signature and honest degraded-state comms.
Security Caller identity end to end: Entra ID on every channel, and production tools act as the signed-in user — a user sees only what their own permissions allow, in Dataverse or in Salesforce/ServiceNow/SAP via each connector's per-user OAuth. Environment-level DLP policies govern every connector the agent may touch. No secrets live in agent content; the prototype tier carries synthetic data only, stamped as such. A maker with environment access can still author a badly-scoped tool; the publish gate and transcript spot-audits are process controls, not technical ones. Prompt injection through knowledge content is mitigated by curated sources, not eliminated.
Cost Optimization The prototype tier costs nothing beyond existing licensing — file knowledge, no infrastructure. Production billing is Copilot Studio capacity (message-based) plus connectors the tenant mostly already licenses. Scale spend is deferred until the pilot proves value; teardown is one command. Message-based billing needs a usage estimate before broad rollout; an agent shared tenant-wide without that estimate is the classic surprise-bill path. Model the pilot's transcript volume first.
Operational Excellence Everything-as-code: the scaffold is git-versioned YAML, ALM is pac pull/push/publish (CI-able), the operating doctrine itself is versioned (twin playbooks carry every known friction and its fix), and the smoke suite in tools/workshop-smoke encodes each defect the first live runs caught. Copilot Studio analytics provide transcripts and usage for continuous improvement. Environment hygiene is on the customer: security-role grants (we hit the missing prvReadbot role live) and connection ownership need a named admin. The runbook names the dependency; it can't remove it.
Performance Efficiency Deterministic business rules live in skills — computed in the turn, no extra service hops. Small curated knowledge keeps retrieval fast and grounded. The production tier pushes queries down to the system of record instead of syncing data out. Model series is a per-agent setting, tunable without redesign. Turn latency is dominated by the LLM, seconds not milliseconds — set that expectation. RAG over file knowledge is for curated corpora; large document estates belong in indexed sources (SharePoint), not uploaded files.

Failure modes and their prevent/detect/respond controls are in the production step's table above — bring both to the architecture review.

Step 6when you're ready

Go to production

The prototype answers from a synthetic file so it works on day one. A production deployment swaps that file for tools that query live systems — and makes sharing, risk, and monitoring deliberate.

Swap file knowledge for live tools

  1. Put the data where it lives

    The stack ships data/technicians.csv and data/service_requests.csv — import them as SharePoint lists to start, or map to where this data already exists: Dynamics 365 Field Service tenants have the roster and work orders in Dataverse (bookableresource, msdyn_workorder).

  2. Add connector tools in the portal

    Copilot Studio → your agent → Tools → Add → Connector (SharePoint Get items, or Dataverse). The portal binds the connection and generates the capabilities/tools/*.mcs.yml — connection references are tenant-specific, which is why the library doesn't ship pre-baked tool YAML.

    Authentication mode matters more than any other setting. Tools must act as the signed-in user so the agent sees only what the caller can see. A service-principal connection reads everything in the tenant — the most common and most expensive mistake in this pattern.
  3. Retire the demo file

    Remove field-service-operations-data.md and its sidecar from capabilities/knowledge/files/, push, publish — the skills don't change; they define the procedure regardless of where the rows come from.

  4. Re-verify

    Run all five checks again against live data — recompute the expected answers from the real roster first. Then share to the Teams channel, deliberately.
